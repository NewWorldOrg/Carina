# デプロイ契約

Carina のイメージにリバースプロキシは入っていません。画面と API を1つのオリジンに
まとめるのは、イメージの外に置いた振り分けの仕事です。

この文書は、そのために満たさなければならない契約と、契約を満たす構成例を持ちます。

## ルーティング契約

満たすべきものはこの2本だけです。

| 受けるパス | 送り先 |
| --- | --- |
| `/api/*` | `role=app`（REST・SSE・TS ストリーム・NDJSON の一括） |
| それ以外 | `role=web`（ページ・`/_next/*`・`favicon.ico`・`manifest.webmanifest`） |

どのプロキシを使うかは選べます。契約が2本しかないのは、k8s でも compose でも同じ
2本で同一オリジンが成立するようにするためです。

## 契約を満たさないとどうなるか

画面と API が別のオリジンに出た瞬間、認証は動きません。「動くけれど少し不便」では
なく、入口が閉じます。

- ブラウザは別オリジンへの `fetch` にセッション Cookie を付けません。ログイン
  そのものが成立しません。
- 状態を変える要求は `Origin` ヘッダが API 自身のオリジンと一致することを求めます。
  別オリジンからの要求は 403 で断られます。ここを通すには送り側が `Origin` を
  偽らねばならず、それは CSRF の防御を自分で外すことです。
- iPad の Safari はサードパーティ Cookie を既定で遮断します。PC で動いても iPad で
  だけ入れない、という形で出ます。
- `EventSource` と `<video>` は資格情報のヘッダを付けられません。同一オリジンの
  Cookie が唯一の運び手です。

つまり「正しく構築しないと動かない」構成です。代わりに、満たすための構成をここに
置いています。

## 前段からのヘッダ

app は既定では前段を信用しません。`X-Forwarded-Proto` を信じる相手を名指しして
はじめて、TLS を終端したのが前段であることを知ります。

| 変数 | 意味 |
| --- | --- |
| `CARINA_KNOWN_PROXIES` | 前段のアドレス。区切りはカンマまたは空白 |
| `CARINA_KNOWN_NETWORKS` | 前段のネットワークを アドレス/プレフィクス で |

どちらも空のままだと、前段が https で終端していても app は要求を平文の http として
読みます。その結果は2つで、どちらもログイン画面に出ません。

- セッション Cookie から `Secure` と `__Host-` が落ちる
- IdP に渡す redirect URI が `http://` で組まれ、登録済みの `https://` と一致せず
  認証の完了後にはじめて弾かれる

これが黙って起きないように、app は起動時に何を信用しているかを1行出します。何も
信用していなければ警告として出ます。加えて、前段を名乗る要求が最初に1つ届いた
ときに、それが採られたのか無視されたのかを、送信元のアドレスとともに1度だけ
出します。無視されていた場合はそのアドレスを上の変数に足せば直ります。

## compose のリファレンス構成

開発用の `compose.yml` にも同じプロキシが入っています。省くと開発のときだけ画面と
API が別オリジンになり、Cookie・SameSite・iPad の前提が開発環境で再現できず、認証の
不具合が本番でしか出ない形になるためです。

| サービス | 待ち受け | 送り先 |
| --- | --- | --- |
| `proxy` | ホストの `PROXY_PORT`（既定 8000） | `/api/*` → `CARINA_APP_ORIGIN`、それ以外 → `CARINA_WEB_ORIGIN` |

| 変数 | 既定 | 意味 |
| --- | --- | --- |
| `PROXY_PORT` | `8000` | プロキシをホストのどのポートに出すか |
| `CARINA_APP_ORIGIN` | `http://app:8080` | 同じ compose の app |
| `CARINA_WEB_ORIGIN` | `http://host.docker.internal:8080` | 画面。別のリポジトリで動かしているならホスト側のポートを指す |

振り分けの中身は `docker/proxy.conf.template` です。SSE と TS ストリームを止めない
ため、バッファリングを切り、読み書きの時間切れを長く取っています。

`app` の直接公開（既定 8081）はそのまま残してあります。プロキシは別のポートに増える
だけなので、動いているものを止めずに入れられます。

### 既存の環境をプロキシへ寄せる

1. `docker compose up -d proxy` でプロキシだけを足す。app も画面も止めません
2. `curl -i http://<ホスト>:8000/api/health` が 200、`curl -i http://<ホスト>:8000/`
   が画面を返すことを確かめる
3. 画面を開き、ログインしてから、`/api/*` への要求に Cookie が付いていることと
   `Set-Cookie` の属性を実機で確かめる
4. 以後はプロキシのポートだけを使う。直接公開していたポートは、しばらく残したまま
   にしておけば、戻すときに何も組み直さずに済みます
5. 直接公開をやめるときに `app` と画面の `ports` を落とす。配布時はここまで進めた
   状態が既定です

## k8s のリファレンス構成

`deploy/k8s` に3つ置いています。

| ファイル | 中身 |
| --- | --- |
| `app.yaml` | `role=app` の Deployment と ClusterIP Service |
| `web.yaml` | `role=web` の Deployment と ClusterIP Service |
| `ingress.yaml` | ルーティング契約の2本 |

`role=web` は単独の Deployment として動きます。app と同じ Pod に同居させる必要は
ありません。画面だけを入れ替えても、録画を抱えたプロセスには何も起きません。

Ingress のルールは契約と同じ2本です。`/api` を前に、`/` を後ろに置きます。

```yaml
- path: /api
  pathType: Prefix
  backend: { service: { name: carina-app, port: { name: http } } }
- path: /
  pathType: Prefix
  backend: { service: { name: carina-web, port: { name: http } } }
```

Service は ClusterIP です。外から届く経路は Ingress の1本だけになり、app の認証を
迂回して Service に届く道が残りません。

`app.yaml` の `CARINA_KNOWN_NETWORKS` は Ingress コントローラの Pod が居る
ネットワークです。クラスタの Pod CIDR に合わせてください。ここが合っていないと、
前段が https で終端していても app は平文として読みます。

`ingress.yaml` の注釈はバッファリングを切り、時間切れを長く取るためのものです。
コントローラごとに書き方が違うので、使うコントローラのものに読み替えてください。
契約はあくまで2本のルールであって、注釈の綴りではありません。

ホスト名は例です。IdP に登録する redirect URI はホスト名ごとに要るので、ホストを
決めてから `https://<ホスト>/api/auth/oidc/callback` を IdP へ先に登録します。
登録前でも authorize までは通ってしまい、認証を終えたところではじめて弾かれます。
